## 二、CI 与凭据

仓库 Secrets（已由 API 写入，值只存在 GitHub 侧）：

| Secret | 用途 |
|---|---|
| `GH_PAT` | 采集器的 fine-grained PAT（5000 次/时；不配会回退 `GITHUB_TOKEN` 的 1000 次/时） |
| `CLOUDFLARE_API_TOKEN` | Pages: Edit 直传 |
| `CLOUDFLARE_ACCOUNT_ID` | 账号标识 |

Actions 开关（缺一不可，不设会**静默失败**）：

- `default_workflow_permissions = write`
- `can_approve_pull_request_reviews = true`

两条工作流：

| 工作流 | 触发 | 作用 |
|---|---|---|
| `deploy.yml`（deploy-site） | push 到 main，改动落在 `assets/**` `scripts/**` `crawler/config.json` 或本文件时 | 构建 + 发布 |
| `sync.yml`（sync-data） | 每 12 小时 cron + 手动 | 并入已批准收录 → 采集 → 提交数据 → 构建 → 发布 |

两者共用 `concurrency: pages-publish`，不会交叉部署。

> **注意**：当前 fine-grained PAT 没有 `Actions` 权限，所以无法用 API 手动触发工作流
> （`workflow_dispatch` 返回 403）。手动触发的替代方式：推一个落在上述 paths 里的提交，
> 或在 GitHub 网页上点「Run workflow」。若想用 API 触发，需给 PAT 补 **Actions: Read and write**。

## 三、缓存与安全头

`scripts/prerender.mjs` 生成 `dist/_headers`，规则如下：

```
/*                     → 只放安全头（nosniff / Referrer-Policy / X-Frame-Options）
/assets/css/*          → Cache-Control: public, max-age=31536000, immutable
/assets/js/*           → 同上
/assets/img/*          → Cache-Control: public, max-age=86400
/sitemap.xml, /llms.txt→ Cache-Control: public, max-age=3600
```

三个关键点，都是踩过坑才定下来的：

1. **`/*` 上不能写 `Cache-Control`**。Cloudflare Pages 对同一请求匹配到的多条规则是**拼接**同名
   header，而不是覆盖。起初 `/*` 写 `max-age=0, must-revalidate`、`/assets/*` 写一年 immutable，
   实测 CSS 拿到的是 `public, max-age=0, must-revalidate, public, max-age=31536000, immutable` ——
   浏览器取第一个，assets 的长缓存等于没设。HTML 的 `max-age=0` 交给 Pages 默认值即可。
2. **assets 的长缓存靠内容指纹兜底**。`scripts/build-dist.sh` 会把 `style.css` / `app.js` /
   `data.js` 重写成 `xxx.css?v=<sha256前12位>`，内容一变 URL 就变，所以敢用一年 immutable。
   zone 级 `browser_cache_ttl` 已被设为 **0（Respect Existing Headers）**，否则它会统一改写
   `/assets/*.js|.css` 的 max-age（gethub.cn 踩过 4 小时窗口）。
3. **图片没有指纹**，所以单独压到 1 天 —— 否则换了 OG 图，社交平台会长期吃旧图。

zone 级设置（已通过 API 调整）：

| 设置 | 值 | 原因 |
|---|---|---|
| `browser_cache_ttl` | `0` | 让 `_headers` 说了算 |
| `always_use_https` | `on` | HTTP 强制 301 到 HTTPS（已验证） |
| `min_tls_version` | `1.2` | 原为 1.0，过旧 |
| `automatic_https_rewrites` | `on` | 保持默认 |

## 四、www 收敛

目标：`www.skillsbin.cn/*` → 301 → `https://skillsbin.cn/*`。

**走过的弯路**：一开始在 `dist/_redirects` 里写

```
https://www.skillsbin.cn/* https://skillsbin.cn/:splat 301
```

线上实测 www 仍返回 200。原因：**Cloudflare Pages 的 `_redirects` 只按路径匹配，source 写不了域名**，
带 scheme 的 source 会被当成普通路径而永不命中。

**当前方案**：独立 Pages 项目 `skillsbin-www`，产物只有一个 `_redirects`：

```
deploy/www-redirect/_redirects
  /* https://skillsbin.cn/:splat 301
```

自定义域挂在 `www.skillsbin.cn` 上，于是「路径 `/*`」就等价于「www 的所有请求」。

**备选方案**（更正统，但当前 CF 令牌没有 Zone→Rulesets 权限）：

```
zone 级 Single Redirect Rule
  expression: (http.host eq "www.skillsbin.cn")
  action:     redirect 301 → concat("https://skillsbin.cn", http.request.uri.path)
```

> 未做 301 之前，www 与主域返回相同内容，靠每页的
> `<link rel="canonical" href="https://skillsbin.cn/...">` 已能避免重复收录，
> 所以这不是上线阻塞项。

## 五、日常运维

```bash
# 改前端/模板后重新发布（CI 会自动跑，也可以在本地验证）
NODE_BIN=$(command -v node) bash scripts/build-dist.sh

# 本地预览产物
cd dist && python3 -m http.server 4173

# 采集一轮（本地需要 PAT；raw 走 Contents API 回落，见采集器说明）
node crawler/crawl.mjs --content-via api --concurrency 6 --max-wait 50
```

发布链路：`git push` → Actions 构建 → wrangler 直传 → 两个自定义域同时生效。
数据链路：12 小时 cron → 采集 → 提交 `data/` → 构建 → 发布。
